# PR incremental delivery

Read in full only after the affirmative optional ZIP decision in the [PR skill](../skills/miniloot-implement-pr/SKILL.md). This procedure applies only on positively identified Codex Cloud after approved commit and push are complete and verified. Use the immutable initial installable baseline and verified final published SHA already recorded by that workflow. Delivery is independent of implementation/publication and of `cloud-update-delivery.md`; it authorizes no new commit, push or physical installation. Delivery failures never roll back or invalidate correctly completed commits, pushes or implementation.

- Generate exactly one incremental ZIP ending in `_installer.zip`, using a reliably determined final addon version in its name, otherwise the final published short SHA. Use only final runtime file contents that differ from the original baseline, including necessary new installable files; exclude unchanged files and reverted intermediate changes. Never generate a full distribution or add a library management system.
- The ZIP is extracted directly into `Interface/AddOns`. Map repository-root addon files into `MiniLoot/`, for example `MiniLoot.lua` to `MiniLoot/MiniLoot.lua`; preserve all other runtime files under `MiniLoot/` with their correct relative subdirectories and add no outer wrapper directory. Exclude documentation, `.agents`, `AGENTS.md`, tooling, tests, infrastructure, temporary files and packaging artifacts that are not installed addon content.
- List deleted installable paths separately in Portuguese for manual removal. Never encode deletions as artificial ZIP entries. If only deletions remain and no non-empty runtime content can be packaged, report the removals without generating an empty ZIP.
- Before delivery, validate archive integrity, non-empty packaged content, entry paths (all under `MiniLoot/`, without absolute paths, traversal or extra wrappers), and each entry's exact final published content against the baseline-derived runtime file list. Record the packaged file count, local byte size and local SHA-256 when available or inexpensive to calculate.
- Preserve normal Codex download delivery. Upload the exact same validated final ZIP with the official Google Drive connector's `upload_file`, its supported file reference mechanism, the final filename, MIME type `application/zip`, and `parent_folder_id` = `11Q6kE7jwPX3gxicCDjcM1FOEtogNUpbO` (`Codex Artifacts/MiniLoot`). Never regenerate or modify the ZIP for Drive. Do not introduce rclone, manual OAuth, API keys, secrets, external dependencies or alternate upload systems.
- After upload, read back the returned file ID using `get_file_metadata` with `id,name,parents,size,webViewLink`. Confirm existence by that ID, the exact filename/title, the destination folder ID in `parents`, and remote size equal to the local byte count when `size` is available. Record the returned link/ID when available. Do not require `trashed`. If remote size is unavailable, report the limitation without claiming size verification. Declare `Google Drive: OK` only after valid readback; an upload response alone is never success.
- Report compactly in Portuguese the ZIP name, packaged file count, local size, SHA-256 when available, Codex download link when available, Drive status and returned link/ID, and manual removals or explicitly none. Report actual upload, readback or Codex download delivery errors separately. Connector unavailability is a delivery failure; never disguise it as success or invalidate a correctly completed implementation or valid local ZIP because a delivery channel failed. Attempt the other delivery channel even if one fails.
