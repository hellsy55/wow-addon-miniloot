# Maintenance runtime

After all history gates and controlled `branch --no-track` creation, preparation reads tracking once with `git config --local --no-includes --null --get-regexp` and an anchored POSIX expression limited to the mode's branches. NUL-terminated key/newline/value records are parsed without stripping bytes. Missing or single incorrect values are written individually; single correct values are left untouched. Duplicate values (even identical), malformed records, and inconsistent command results fail explicitly before any tracking write. Exit 1 means no matching values only with completely empty stdout/stderr; all write failures stop preparation without retry or rollback. Development never queries master. Local tracking is the only configuration scope inspected or changed. Successful invocation counts are `12 + k` in development, `20 + k` in update, and `14 + k` in development starting on Cloud work, where `k` is the number of tracking keys written. Failures can leave earlier authorized branch creation or writes in place; partial preparation is not success.

For the offline test suite in a positively identified Cloud session, the agent must authorize `MINILOOT_MAINTENANCE_HOST=codex-cloud` and explicitly set `MINILOOT_TEST_CLOUD_WORK=1` before starting Python. The suite opt-in forwards `cloud_work=True` to the existing resolver on Linux only; it neither establishes Cloud identity nor sets the host marker automatically. All resolver checks still apply, including the canonical Cloud root. Without that opt-in, normal Linux UID 0 selection remains in effect; Windows retains its existing trusted selection. No additional Git subprocess is used for this bootstrap.

The default Linux ownership policy remains UID 0. A narrowly scoped alternative handles the observed managed Cloud user namespace only when `prepare(..., cloud_work=True)` explicitly passes that context to `resolve_git`. Direct resolver calls default to no Cloud exception. The exception additionally requires Linux, `MINILOOT_MAINTENANCE_HOST=codex-cloud`, and the canonical checkout root `/workspace/wow-addon-miniloot`. The agent must positively identify Cloud from real session/task metadata before authorizing that marker and `--cloud-work`; neither the flag nor the environment variable independently proves host identity. CLI argument meanings are unchanged.

Only a rejection specifically caused by consistently remapped UID 65534 ownership can reach the alternative. All process UID/EUID/GID/EGID values must equal 1000, supplementary groups must be empty, and both `/proc/self/uid_map` and `/proc/self/gid_map` must contain exactly one numeric mapping equivalent to `1000 0 1`. These files are read only while evaluating the exception. UID 65534 does not establish the original inode owner's identity.

The resolved executable must remain a regular executable outside the checkout, directly within `/usr/bin`, `/bin`, or `/usr/local/bin`; distribution symlinks such as `/bin` to `/usr/bin` are resolved first. The executable and every resolved ancestor through `/` must consistently have UID/GID 65534:65534, no group/world write bits, no effective write access, and a read-only mount confirmed independently for each path by `os.statvfs(path).f_flag & os.ST_RDONLY`. Effective permission checks require `os.access` support for `effective_ids=True`, including effective execution permission on the executable. Missing APIs, unreadable or malformed mappings, unsupported identities, writable paths, read-write mounts, and unavailable evidence reject the exception explicitly. No write probes, discovery subprocesses, Git version probes, PATH fallback, installations, or ownership changes are introduced.

This boundary depends on the integrity of the administered runtime and the agent's metadata-based authorization. It provides no cryptographic authenticity guarantee and cannot prevent privileged replacement or later environment changes between validation and execution. Windows selection and the ordinary UID 0 Linux path retain their existing policies. Windows mock tests demonstrate policy behavior only; real Linux Cloud compatibility must be validated again after separately authorized publication and Republish.

The preparation helper resolves Git once per invocation, without launching discovery subprocesses or changing PATH. Windows requires `C:\Program Files\Git\cmd\git.exe`, a regular file whose resolved target stays inside that Git installation and outside the checkout. Linux searches only `/usr/bin`, `/bin`, and `/usr/local/bin` using filesystem discovery, then requires an executable regular file outside the checkout; its resolved path and all ancestors must be root-owned and not group/world-writable. Missing or rejected installations fail explicitly without a PATH fallback or installation. Linux distribution symlinks are resolved before validation. These checks assume the Windows installation ACLs and the Linux system administrator/runtime are trusted; they do not verify signatures, binary contents, or prevent privileged replacement between validation and execution. No Git version probe is added. Linux policy tests on Windows are simulations; operational Cloud compatibility requires a later Cloud validation.

Unexpected Git exit codes report the real code, command, and available stderr/stdout (in that order); empty channels are explicitly identified when both are empty. Launch failures have a separate diagnostic. Each displayed command/channel is escaped and bounded to 1600 characters after redacting URL userinfo/query values, authentication headers, common credential assignments, and recognizable GitHub tokens. This is best-effort redaction of common formats, not a guarantee for arbitrary unlabeled secrets. Diagnostics are not persisted and do not authorize retries, HTTPS fallback, installation, or publication. Allowed Git exit codes and the CLI failure contract (`error` JSON field, exit 1) are unchanged.

Load at the first Python-helper or prepared-local-checkout stage, not for entry or remote-only PR URL/metadata/paths/diff review. Use existing Git and Python 3 only; never install dependencies or modify PATH. Reuse the frozen host/root and environment eligibility from AGENTS.md. Discover Python once with `python3 -B scripts/maintenance_runtime.py` on Linux or existing `python`/`py -3` on Windows. If launchers fail, inspect trusted existing `%LOCALAPPDATA%/Programs/Python/Python*/python.exe` installations. Stop clearly if Python 3 cannot be determined. Add the absolute executable returned in JSON to that context and reuse it throughout the workflow with `-B` or PYTHONDONTWRITEBYTECODE=1. Do not rediscover it in setup, branch synchronization, PR stages or an installation handoff.

Run `<absolute-python> -B scripts/prepare_update.py --mode update` once for authorized update, or `--mode development` once for PR/development. Apply any bootstrap option only through the already selected environment adapter. Explicitly target the validated root on every execution. The helper validates exact fetch/push URLs, fetches explicit destination refspecs without changing remote.origin.fetch, rejects dirty/unfinished/unpublished/divergent state, and sets tracking. It never merges, resets, commits, pushes, or advances existing local branches. Update alone may add missing upstream. Development does not touch master/upstream. Partial ref preparation or network failure is not success.

Keep the successful preparation JSON (`root`, `mode`, `branch`, `created`, `refs`, `behind`, and `local_tips`) as the mechanical baseline. Existing fields and remote keys in `refs` are unchanged. `local_tips` maps `new-features` to its full local SHA in both modes and additionally `master` in update mode; it never substitutes the operational `work` branch. These tips are collected with the remote refs after fetch, history gates, and any controlled branch creation. Reuse `local_tips` for the required local/remote comparisons; upstream-to-new-features ancestry is not returned and must still be checked separately. Zero `behind` counts alone never prove a no-op. Reuse existing evidence while its refs/index/worktree remain unchanged; invalidate only affected facts after mutations or confirmed external operations. A fetch invalidates affected remote SHAs and comparisons; fast-forward or integration invalidates affected local tips, behind counts, comparisons, and ancestry. Recalculate those facts from the current refs before another gate or final verification, without repeating preparation or fetching redundantly. The JSON is a snapshot, not a persistent cache. Separately fast-forward branches behind origin in the authorized workflow. Never repeatedly fetch/pull or run preparation just for startup. A failed preparation stays pending; do not reuse partial JSON as successful evidence or restart network operations after transport has been classified unavailable. Offline tests: `<absolute-python> -B -m unittest discover -s scripts/tests -v`. Validate syntax with ast.parse to avoid bytecode artifacts.
