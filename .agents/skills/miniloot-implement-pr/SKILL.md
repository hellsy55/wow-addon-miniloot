# Implement a MiniLoot PR

Follow AGENTS.md. Freeze only host/root and record environment action eligibility at entry; explicitly target the validated root on every Git execution, never its parent. Accept only PR URLs belonging to `Vladinator/wow-addon-miniloot`; reject other upstream repositories. Local work is only on new-features, never master; local preparation must reject unexpected changes or unfinished Git operations before checkout-dependent work.

Validate the PR URL, then retrieve compact remote metadata and changed paths read-only: show number, title, file count, additions, deletions, and all affected paths before retrieving the PR diff. Initial reading of that remote diff does not require Python discovery or prepare_update.py when strictly read-only and independent of local branch state. Do not fetch into local refs, switch branches, run Python helpers, or infer compatibility with local customizations in this phase. Read full remote files only when the PR diff is insufficient. Remote metadata failures remain pending; do not invent results.

Load [cloud environment](../../references/cloud-environment.md) only for confirmed Cloud. Immediately before the first operation requiring a prepared local checkout (comparison with new-features, local customization compatibility analysis, application, checkout, merge, staging or commit), or any Python helper, read [maintenance runtime](../../references/maintenance-runtime.md), discover and freeze Python once, and prepare once with `--mode development` using only the selected adapter's bootstrap option. Successful preparation, real new-features and the tip-equality gate below are mandatory before semantic comparison with the local fork or application. Preserve dirty/unfinished/unpublished/divergent-history and Cloud work gates; preparation alone may perform its guarded bootstrap checkout. Reuse the same runtime, preparation and resulting refs throughout; no repeated fetch without concrete invalidation. Local Windows retains its canonical path; only its specific transport failure loads the fallback routed by AGENTS.md. Never touch master/upstream unnecessarily in development preparation.

After successful preparation, use the returned `behind["new-features"]` count. If it is greater than zero, run ONLY `git merge --ff-only origin/new-features` before checkout-dependent PR analysis or application. Do not fetch again. Then prove local new-features == origin/new-features by comparing a successful `git rev-parse new-features` result with the prepared origin/new-features SHA, including when behind is zero; reread the remote-tracking ref only if it changed. A failed fast-forward, failed comparison, or unequal tips stops the workflow as PENDENTE. Ahead/divergent history remains blocked by the helper for human review; never reset, overwrite, or rewrite local commits. The helper itself continues to preserve existing local branches and never performs this fast-forward.

Immediately after successful preparation and confirmed tip equality, record the full SHA of the initial installable new-features state, before the first PR implementation modification. Preserve this SHA as the immutable installer baseline throughout the implementation; never replace it with the state immediately before the final PR commit. After approved commit and push, verify and record the final SHA actually published in origin/new-features, containing exactly the approved result.

If root validation or any mandatory Git check fails, STOP dependent workflow operations and report the workflow as PENDENTE. Never treat a failed branch, status, diff, ancestry, fetch, or other mandatory check as successful completion. Respect documented non-error exit codes. Do not offer installation or execute the installer from a failed Git workflow; a "not a git repository" failure must never be followed by fetch, merge, push, the installation menu, or installation.

After the preparation/tip-equality gate, reuse the remote metadata/diff and compare the PR with current local customizations. Open only relevant local functions and necessary context; do not repeat remote reads without concrete invalidation.

Before modifying anything, explain in Portuguese what we gain, what may change, what we lose, what stays the same, and interactions with our customizations. For a small PR offer apply or ignore. For a large/complex PR offer: a) apply as-is; b) apply adapted; c) ignore a specified part; d) do not apply. Wait for the user's decision before edits. Use exactly one read-only deep_reviewer only when AGENTS.md criteria justify it. Review never grants implementation approval.

Implement only the selected scope and validate the resulting behavior. Never resolve conflicts automatically; use the update skill's conflict reference if conflicts occur. Stage only relevant files. Show staged name-only, name-status, staged stat, and COMPLETE staged diff, then wait for explicit commit approval. Commit only after that approval, with the required English subject format and configured user identity. Push new-features only after commit and necessary publication approval; never publish unreviewed preexisting commits.

When PR implementation results in a commit, its English body must reference the PR number and source `Vladinator/wow-addon-miniloot` (for example, `Implement PR #123 from Vladinator/wow-addon-miniloot`). Do not add an AI signature. This requirement does not change the mandatory complete checkpoint and explicit approval immediately before the commit.

Verify origin/new-features contains exactly the approved result before the local Windows installation menu and wait. On Cloud/Linux, only state that physical installation is a local Windows step; do not offer a menu or execute PowerShell. Choosing installation authorizes execution of the external script via the install skill without another confirmation. Report verified outcomes and any pending decisions or errors compactly in Portuguese.

## Optional incremental installer on Codex Cloud

This optional delivery applies only on positively identified Codex Cloud, after the PR implementation's approved commit and push are complete and verified. It is independent of `cloud-update-delivery.md`; do not load or use that reference for this PR workflow. Preserve all existing preparation, conflict, approval, commit, publication and Windows installation rules. ZIP generation or delivery never authorizes physical installation and is never a prerequisite for completing the implementation.

Compare the immutable initial installable SHA with the verified final published SHA. If there is no net functional/runtime installable change, do not offer an installer or generate an empty ZIP. Otherwise ask exactly: `Deseja que eu gere também um ZIP incremental pronto para instalar?` Wait for the answer. If the user declines, finish normally. Only an affirmative answer authorizes generating the installer below, without another commit/push or installation.

- Generate exactly one incremental ZIP ending in `_installer.zip`, using a reliably determined final addon version in its name, otherwise the final published short SHA. Use only final runtime file contents that differ from the original baseline, including necessary new installable files; exclude unchanged files and reverted intermediate changes. Never generate a full distribution or add a library management system.
- The ZIP is extracted directly into `Interface/AddOns`. Map repository-root addon files into `MiniLoot/`, for example `MiniLoot.lua` to `MiniLoot/MiniLoot.lua`; preserve all other runtime files under `MiniLoot/` with their correct relative subdirectories and add no outer wrapper directory. Exclude documentation, `.agents`, `AGENTS.md`, tooling, tests, infrastructure, temporary files and packaging artifacts that are not installed addon content.
- List deleted installable paths separately in Portuguese for manual removal. Never encode deletions as artificial ZIP entries. If only deletions remain and no non-empty runtime content can be packaged, report the removals without generating an empty ZIP.
- Before delivery, validate archive integrity, non-empty packaged content, entry paths (all under `MiniLoot/`, without absolute paths, traversal or extra wrappers), and each entry's exact final published content against the baseline-derived runtime file list. Record the packaged file count, local byte size and local SHA-256 when available or inexpensive to calculate.

Upload the exact same validated final ZIP with the official Google Drive connector's `upload_file`, its supported file reference mechanism, the final filename, MIME type `application/zip`, and `parent_folder_id` = `11Q6kE7jwPX3gxicCDjcM1FOEtogNUpbO` (`Codex Artifacts/MiniLoot`). Confirm existence by that ID, the exact filename/title, the destination folder ID in `parents`, and remote size equal to the local byte count when `size` is available. Report actual upload, readback or Codex download delivery errors separately. Connector unavailability is a delivery failure; never disguise it as success or invalidate a correctly completed implementation or valid local ZIP because a delivery channel failed.
