# Independent branch synchronization

Use the environment-specific validated root from AGENTS.md on EVERY execution. Failure of root, status, branch, ancestry (except documented exit 1), fetch, comparison or publication stops dependent work and leaves it PENDENTE. Never interpret an error as no-op or offer installation on failure.

1. Reuse the frozen context and the single successful update preparation from [maintenance runtime](../../../references/maintenance-runtime.md); if not yet prepared, run it once with the selected adapter. Reuse its explicitly fetched origin/new-features, origin/master and upstream/master SHAs and behind counts. Require real new-features after any authorized bootstrap. BEFORE checkout or integration, compare successful local new-features/master tip SHAs with those prepared refs and check upstream/master ancestry in new-features (exit 0/1 are defined; other exits are errors). Complete no-op requires successful checks, local new-features == origin/new-features, local master == origin/master == upstream/master, and upstream/master ancestor of new-features, exactly as before. If proven, skip steps 2–7 and go directly to step 8: no checkout, merge, repeated fetch, full diff, semantic review, commit or push. Equality already verifies origin/new-features against the local result. Any failed preparation/check/comparison/verification remains PENDENTE, never no-op.
2. If new-features is behind origin/new-features, fast-forward with git merge --ff-only origin/new-features. Do not publish preexisting local commits; any ahead/divergent state stops for human review. Recalculate upstream analysis after changing the base. No automatic origin divergence merge.
3. Reuse the no-op gate's upstream/master-to-new-features ancestry unless step 2 changed the base; then recalculate it. `git merge-base --is-ancestor upstream/master new-features`: exit 0 means no incoming upstream, exit 1 means continue, other exits are errors. When incoming exists, record `git merge-base new-features upstream/master`, the range `<base>..upstream/master`, and `git rev-list --count` for that range. BEFORE merge, retrieve changed paths/name-status for that range and `<base>..new-features` and compare paths/modules. This metadata overlap gate is mandatory; no early full diff. If upstream introduces libraries/externals, stop for human review regardless of overlap. If there is no plausible overlap with customizations, skip semantic review. For plausible overlap, open only relevant diffs/functions and necessary context; use deep_reviewer only per AGENTS.md difficult-case criteria, never for routine metadata or synchronization.
4. If incoming exists, integrate upstream/master DIRECTLY into new-features with git merge --no-commit upstream/master. Preserve merge semantics. Fast-forward can complete without a commit. Before EVERY commit, including a merge commit, show `git diff --cached --name-only`, `git diff --cached --name-status`, `git diff --cached --stat`, and COMPLETE `git diff --cached` without size exceptions, then obtain explicit approval immediately before `git commit`. Any subsequent staged change requires a new complete checkpoint and approval. Prior implementation approval is insufficient. Conflicts always require human choice via [merge conflicts](merge-conflicts.md); never auto-resolve.
5. Push new-features only when advancement requires publication and all required commit/publication approvals exist. Never publish unreviewed previous local commits. Failed push leaves publication pending.
6. Independently synchronize master DIRECTLY from upstream/master. The helper proves origin/master is an ancestor of upstream/master and local master is an ancestor of origin/master; revalidate if state changed. Fast-forward master to origin/master if needed, then upstream/master. Never merge new-features into master or master into new-features; no master merge commit or fork-only history. Push only safe upstream advancement. Avoid checkout if already current.
7. Return to new-features, including after master failures when safe. Verify origin/new-features tip equals the approved local result using the updated tracking ref from successful push; if insufficient, use one explicit verification fetch, not repeated fetches. Report failure as pending.
8. Report verified results compactly and use the frozen environment capabilities to follow AGENTS.md's completion routing and exact installation menu. Update never authorizes installation; load its skill only after a valid installation choice or unequivocal direct request. Do not load physical-installation details just to complete synchronization or a no-op.
